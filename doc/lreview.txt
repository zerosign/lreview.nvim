*lreview.txt*   Unified MR/PR Code Review inside Neovim            August 2026

==============================================================================
INTRODUCTION                                                 *lreview-intro*

|lreview.nvim| is a fast, asynchronous code review plugin for Neovim that 
unifies review operations across GitHub, GitLab, and custom code hosts. It 
leverages local SQLite caching for sub-millisecond thread loading and offloads
networking and sync operations to isolated libuv background worker threads.

Main Features:
- Asynchronous worker threads (`uv.new_work`) with MessagePack serialization.
- Centralized debounced Sync Bus (~80ms coalescing) and in-memory diff cache.
- Idempotent submit driven by a `push_ops` outbox: every mutation is one row,
  committed the moment its call succeeds, so retries never double-post.
- Adapter capability system for safe multiplatform feature queries.
- Repo topology-aware materialization (`checkout` vs `worktree`).
- Summary panel with dual view modes (Threads & Files table) and verdict
  short-circuits (`A` to approve, `R` to reject).
- Floating verdict confirmation popup window.
- Conflict detection with `:LocalReviewConflicts` to keep or accept each side.
- Offline issue tracker cache with FTS5 search, so an MR's linked issues can be
  read without a network round trip.

INSTALLATION                                          *lreview-installation*

Using |lazy.nvim|:
>lua
  require("lazy").setup({
    {
      "zerosign/lreview.nvim",
      dependencies = {
        "kkharji/sqlite.lua", -- SQLite wrapper dependency
      },
      opts = {
        defaults = {
          db_path = vim.fn.stdpath("data") .. "/lreview/lreview.db",
          topology = "simple", -- "simple" | "monorepo-single" | "monorepo-multi"
          db = {
            busy_timeout_ms = 5000,
            keep_days = 30,
            auto_housekeep = true,
          },
          ui = {
            decor = "both",
            float = { width = 0.5, height = 0.6 },
          },
          open = { method = "checkout" },
        },
        ["github\\.com"] = {
          adapter = "github",
          provider = "gh",
          host = "github.com",
        },
        ["gitlab\\.com|gitlab\\..*"] = {
          adapter = "gitlab",
          provider = "glab",
          host = "gitlab.com",
        },
      },
    }
  })
<

CONFIGURATION                                        *lreview-configuration*

The plugin is configured by passing an options table to `setup()`:
>lua
  require("lreview").setup(opts)
<

Global Settings ~
Inside the `defaults` block of your configuration:

  `db_path`           (string)
                      Absolute path to the SQLite cache file.
                      Default: `vim.fn.stdpath("data") .. "/lreview/lreview.db"`

  `topology`          (string)
                      Repository topology classification for branch materialization.
                      Options: `"simple"`, `"monorepo-single"`, `"monorepo-multi"`.
                      Default: `"simple"`

  `db.busy_timeout_ms` (number)
                      SQLite busy lock timeout in milliseconds.
                      Default: `5000`

  `db.keep_days`      (number)
                      Number of days to preserve closed/merged pull requests.
                      Default: `30`

  `db.auto_housekeep` (boolean)
                      Whether to auto-run SQLite database housekeeping on open.
                      Default: `false`

  `ui.decor`          (string)
                      How inline comment indicators are rendered in buffers.
                      Options:
                        "both"         Render both signs and virtual text.
                        "sign"         Render sign column symbols only.
                        "virtual_text" Render virtual text only.
                        "none"         Disable inline annotations.
                      Default: `"both"`

  `ui.float.width`    (number)
                      Width of floating thread panel (percentage of window).
                      Default: `0.5` (50%)

  `ui.float.height`   (number)
                      Height of floating thread panel (percentage of window).
                      Default: `0.6` (60%)

  `issues.per_page`   (number)
                      Hub page size for the sequential issue pull.
                      Default: `50`

  `issues.max_pages`  (number)
                      Hard stop on the paging driver, so a huge tracker cannot
                      run away. Default: `20`

  `issues.stale_after_min` (number)
                      Age past which `:LocalReviewIssues` refreshes the cache
                      before opening. Default: `30`

  `open.method`       (string)
                      Action to execute when starting a review branch.
                      Default: `"checkout"`

Per-Domain Configurations ~
Keyed by a pattern (Lua matching) matching the remote repository domain (e.g.
`["gitlab\\.mycompany\\.com"]`). Supports these configuration attributes:

  `adapter`           (string) Platform adapter (`"github"` or `"gitlab"`).
  `provider`          (string) CLI binary command to run (`"gh"` or `"glab"`).
  `host`              (string) API host domain.

USER COMMANDS                                             *lreview-commands*

`:LocalReviewQuery` [<scope>]
                      Lists available MRs/PRs for the current repository.
                      `scope` can be "mine" (default) or "all".

`:LocalReviewDetail` [<ref>]
                      Opens the markdown-formatted detail buffer editor for an
                      MR/PR. Supports direct saves (:w) to update titles and
                      descriptions on the remote platform.

`:LocalReviewStart`
                      Resolves the repository target MR, initializes database
                      schema connection, and triggers an asynchronous pull.

`:LocalReviewCreate`
                      Launches an interactive picker flow to select target branch
                      and template, and inputs a title to create a remote MR/PR.

`:LocalReviewBranch` [<name>]
                      Creates and materializes a new review branch/worktree based on
                      the configured repository topology strategy.

`:LocalReviewComment`
                      Adds a local draft comment on the current visually
                      selected line range. Requires an active review.

`:LocalReviewSubmit`
                      Launches the floating confirmation popup window to push
                      local draft inline comments and review verdicts.

`:LocalReviewPull`
                      Triggers an asynchronous worker thread pull (`uv.new_work`)
                      to update comments and threads for the active review.

`:LocalReviewClose` [<number>]
                      Closes the MR/PR on the remote platform and updates the
                      local SQLite database state to "closed".

`:LocalReviewApprove` [<number>]
                      Approves the MR/PR on the remote platform and updates the
                      local SQLite database state to "approved".

`:LocalReviewToggle`
                      Toggles inline annotations (signs & virtual text) on or off
                      for the current buffer.

`:LocalReviewHover`
                      Displays the thread detail floating window for the active
                      discussion thread under the cursor line.

`:LocalReviewSummary`
                      Opens the interactive review summary panel. Supports dual
                      view modes (Threads & Files table), jump, resolve, filter,
                      sort, and direct approve/reject short-circuits.

`:LocalReviewNext`
                      Jumps to the next discussion thread in the active buffer.

`:LocalReviewPrev`
                      Jumps to the previous discussion thread in the active buffer.

`:LocalReviewConflicts`
                      Lists the comments blocking submit, showing your version
                      against the remote's. `k` keeps yours (re-queued for the
                      next submit), `a` accepts theirs, `q` closes.

`:LocalReviewRequestReview`
                      Requests a review from a cached repo user, fetching the
                      user list first when nothing is cached.

`:LocalReviewPullUser`
                      Caches the repository user list for reviewer autocomplete.

`:LocalReviewPullRequest`
                      Caches the open MR/PR list for link autocomplete.

`:LocalReviewIssuePull` [<state>]
                      Pulls the issue list page by page on a worker thread,
                      reporting progress and writing each page as it arrives.
                      <state> is `open` (default), `closed`, or `all`.

`:LocalReviewIssues` [<state>]
                      Picks a locally cached issue and shows its description and
                      discussion. Refreshes the cache first when it is empty or
                      older than `issues.stale_after_min`. The picker goes
                      through `vim.ui.select`, so telescope / fzf-lua /
                      snacks.picker render it in your config.

`:LocalReviewIssue` <number>
                      Shows one issue by number, fetching it from the hub only
                      when it is not already cached. Press `S` in the buffer to
                      re-sync that single issue.

SUMMARY PANEL KEYBINDINGS                               *lreview-summary-panel*

The summary panel (`:LocalReviewSummary`) provides a dual-view inspection tool:

  `g`                 Toggle View Mode: switches between **Threads** view and
                      **Files** table view.
  `f`                 Toggle Filter: toggles between active/drafts and all threads.
  `S`                 Cycle Sort Mode: cycles sorting in Files view (`path`,
                      `comments`, `additions`, `deletions`).
  `o` / `<CR>`        Jump / Open: opens selected thread or file at cursor.
  `s` / `r`           Resolve / Reopen: toggles thread resolved state.
  `d`                 Delete Draft: deletes local draft thread under cursor.
  `p`                 Push Selected: submits selected thread changes.
  `P`                 Push All: submits all pending review changes.
  `u`                 Pull Updates: triggers background async pull job.
  `A`                 Approve MR: short-circuit to approve active MR.
  `R`                 Reject MR: short-circuit to submit request changes verdict.
  `q`                 Close: closes summary panel window.

==============================================================================
THREAD VIEW KEYBINDINGS                                 *lreview-keybindings*

When viewing discussion threads (`:LocalReviewHover`), Neovim displays all threads
for the active line sequentially in a split buffer:

  `r`                 Reply: opens a reply window for the selected thread.
  `e`                 Edit: edit an existing local draft comment.
  `d`                 Delete: delete a local draft comment/reply.
  `s`                 Resolve/Reopen: toggles the resolved status of the thread.
  `P`                 Submit: push all local review comments.
  `q`                 Close: closes the thread view panel.

ADAPTER CAPABILITY SYSTEM                             *lreview-capabilities*

Each platform adapter declares its feature capabilities in a `capabilities` table:

  `review_verdict`   (boolean) Verdict support (Approve / Request Changes).
  `draft_mr`         (boolean) Draft MR creation support.
  `update_mr`        (boolean) MR title/description edit support.
  `close_mr`         (boolean) MR closure support.
  `approve_mr`       (boolean) Direct MR approval support.
  `list_templates`   (boolean) MR template listing support.
  `inline_comments`  (boolean) Line-level inline comment support.
  `resolve_threads`  (boolean) Thread resolution support.
  `batch_submit`     (boolean) Several inline comments in ONE call.
  `atomic_inline_batch` (boolean) That call is all-or-nothing, so nothing can
                       partially land. Drives how lreview commits new threads.
  `verdict_in_review_batch` (boolean) The review event may ride along with that
                       call; otherwise the verdict is its own `submit_verdict`.
  `assign_reviewers` (boolean) Reviewer assignment support.
  `issues`           (boolean) The hub exposes an issue tracker to cache.
  `offline_staging`  (boolean) Draft-then-batch workflow supported.

`atomic_inline_batch`, `verdict_in_review_batch` and `issues` default to false, so
a custom adapter is never assumed to support an atomic batch, an in-batch verdict,
or an issue tracker. (`batch_submit` defaults true for v3 compatibility, but the
engine drives nothing off it today.) See |lreview-verdict-shape| for how the
submit-shape flags change the calls lreview makes.

Query capability support via:
>lua
  local adapter = require("lreview.adapter")
  local supports = adapter.supports(resolved_ctx, "review_verdict")
<

ASYNC THREAD ARCHITECTURE                             *lreview-async-model*

lreview.nvim offloads background operations to isolated `uv.new_work` worker
threads via `lreview.thread`:

- **Isolated Lua States:** Worker threads run in separate Lua environments.
- **MessagePack Serialization:** Communication across the thread boundary uses
  `vim.mpack.encode` and `vim.mpack.decode`.
- **Fast Event Escapes:** All thread completion callbacks run inside libuv fast
  event context and are wrapped in `vim.schedule` before invoking Neovim API calls.
- **Per-Call Callback Slots:** Workers are module-level singletons, so their
  completion closure is created once and must not capture a caller's callback
  (it would then replay the FIRST call's callback forever). Callers arm a
  callback with `thread.arm(key, cb)` before queueing, and the completion pulls
  it with `thread.dispatch_cb(key, ...)` — FIFO, matching libuv's job order.
- **Results Echo Their Inputs:** A worker result carries back the arguments it
  acted on (e.g. `cwd`, `thread_id`, `title`), so a completion never reads a
  stale captured value or acts on the wrong session.
- **Notifications Survive the Boundary:** `vim.notify` is unavailable on worker
  threads, so notifications are accumulated and replayed on the main thread.

CENTRALIZED SYNC BUS & DIFF CACHE                       *lreview-sync-bus*

All propagation across gutter signs, virtual text, and panel redraws is handled
by `lreview.sync`:

- **Debounced Flush:** Action handlers mark buffers dirty via `sync.mark_dirty(buf)`.
  Flush passes coalesce within an ~80ms window using `vim.uv.new_timer()`.
- **In-Memory Diff Cache:** `sync.get_changed_lines(cwd, path)` caches `git diff`
  results per file, rendering gutter decorations in `0.029 ms` per pass (**78.6x faster**).

SUBMIT OUTBOX & ATOMICITY                          *lreview-submit-atomicity*

A comment's state column describes only its CONTENT relative to the hub:
- `DRAFT` (1): Unpushed local comment.
- `SYNCED` (2): Confirmed on the remote forge host.
- `MODIFIED` (8): Locally edited after remote sync.
- `DELETED` (16): Locally soft-deleted, pending remote deletion.
- `CONFLICT` (32): Remote collision detected; blocks submit until resolved.
(Bit 4 is reserved. v3 used it for an `IN_FLIGHT` push lock, which stranded
drafts: the pending-push mask excluded that bit, so an interrupted submit left
comments that were neither pushed nor pushable until a restart.)

Whether a mutation has been SENT is tracked separately, as one row per mutation
in the `push_ops` outbox (lua/lreview/storage/outbox.lua):

    QUEUED -> RUNNING -> DONE | FAILED
    FAILED -> RUNNING                       (retry: same row, refreshed payload)
    RUNNING -> QUEUED + uncertain = 1       (crash recovery)

Guarantees:
- Each success is committed as DONE together with the comment's own transition
  in one `storage.with_transaction(fn)` block, so a later failure in the same
  batch can never re-send a note that already landed.
- `outbox.enqueue` dedupes by (c_id, op): re-running submit never queues the
  same mutation twice. A queued op whose body was edited refreshes its payload
  snapshot rather than adding a second row.
- A failure marks that op FAILED and stops its category, leaving untouched ops
  QUEUED. Nothing is stranded, and `:LocalReviewSubmit` reports the count still
  queued so the user knows to run it again.
- An op interrupted mid-call has an unknown outcome; `outbox.recover_stale()`
  re-queues it flagged `uncertain` and the next reconcile adopts the comment by
  body match instead of posting a duplicate.

Category order is create_thread, reply, edit, delete, verdict — so replies always
land after the thread they belong to, and the verdict last of all.

PUSH OPS, VERDICTS & HUB DIFFERENCES                   *lreview-verdict-shape*

Platforms differ in how a verdict can be delivered, and the adapter declares it
instead of the engine guessing (see `adapter.supports`):

                                          GitHub    GitLab
`batch_submit`                            true      false
`atomic_inline_batch`                     true      false
`verdict_in_review_batch`                 true      false

- GitHub: `POST /pulls/{n}/reviews` creates every inline comment AND sets the
  event in one all-or-nothing call, so the verdict rides along when there are
  new threads, and nothing lands when the call fails.
- GitLab: `glab mr note create` is one note per call. lreview drives that loop
  itself and commits each note as it succeeds, which is what stops a mid-loop
  failure from re-posting notes that already landed. The verdict is a separate
  `glab mr approve` call.
- A verdict chosen with no new threads to attach it to becomes its own op on
  both platforms, so "approve" is never silently dropped.
- `REQUEST_CHANGES` has no glab equivalent. It is reported as a failed op with
  that reason rather than faked with a note or swallowed.

ISSUE TRACKER CACHE                                           *lreview-issues*

The hub's issue list is cached locally (schema tables `issues` + `issue_notes`,
with an FTS5 trigram index) so the reviewer can read what an MR is actually
about without another round trip.

- `:LocalReviewIssuePull [open|closed|all]` fetches page by page on a worker
  thread, writing each page as it arrives and reporting progress. Pages are
  sequential because progress is only meaningful in order, and a short page is
  the end-of-list signal. `defaults.issues` sets `per_page`, `max_pages`, and
  `stale_after_min`.
- `:LocalReviewIssues [state]` reads the cache (refreshing first when it is
  empty or older than `stale_after_min`) and picks through `vim.ui.select`, so
  telescope, fzf-lua, and snacks.picker render it from the user's own config.
- `:LocalReviewIssue {n}` shows one issue by number, fetching it only when
  uncached. Press `S` in the buffer to re-sync that single issue.
- `require("lreview").api.issue_views.referenced(text)` resolves `#123` / `!45`
  / `owner/repo#7` / issues URL references against the cache and returns only
  what is already stored — correlation costs no network.
- GitHub's `/issues` endpoint also returns pull requests; the mapper drops them
  so they are never double-listed against their own MR cache row.
- Closed issues past the keep window are purged by the same garbage collection
  that protects local drafts.


==============================================================================
DATABASE ENGINE & CONCURRENCY                         *lreview-database-engine*

lreview.nvim utilizes `kkharji/sqlite.lua` to access SQLite caches.

SQLite Flavors ~
The plugin automatically detects the running Lua environment:
  - If running in LuaJIT (default in Neovim), it dynamically binds directly to
    the system `libsqlite3.so` using FFI for native execution speed.
  - If FFI is unavailable, it gracefully falls back to `lsqlite3`.

WAL Mode & Concurrency ~
SQLite is opened with Write-Ahead Logging (`PRAGMA journal_mode=WAL;`), enabling
concurrent reads and writes between background worker threads and the main Neovim process.

==============================================================================
GARBAGE COLLECTION                                              *lreview-gc*

SQLite garbage collection runs on database initialization when
`db.auto_housekeep` is set to `true`. Old closed or merged MRs beyond `keep_days`
are purged, while all local drafts (`remote_id IS NULL`) are strictly preserved.
